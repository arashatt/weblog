قاعده‌ای که برای این وب‌سایت گذاشتم یک جمله است: **هیچ کتابخانه‌ای نباید به
مرورگر برسد.** نه برجسته‌ساز نحو، نه موتور ریاضی، نه مسیریاب، نه کتابخانهٔ
تاریخ. هر کاری که می‌شود هنگام ساخت انجام داد، هنگام ساخت انجام می‌شود.

این محدودیت در نگاه اول ریاضت‌کشی بی‌دلیل به نظر می‌رسد. در عمل، بیشتر از
آن‌که دست‌وپاگیر باشد، تصمیم‌ها را جای درستشان می‌نشاند.

## مرزِ ساخت و اجرا

هر قابلیتی در چنین وب‌سایتی دقیقاً یکی از این دو طرف می‌افتد:

| کار | کجا انجام می‌شود | آنچه به مرورگر می‌رسد |
|---|---|---|
| برجسته‌سازی نحو | هنگام ساخت (Shiki) | HTML با سه متغیر رنگ در هر span |
| ریاضیات | هنگام ساخت (KaTeX → MathML) | نشانه‌گذاریِ MathML، بی‌قلم و بی‌CSS |
| تاریخ شمسی | هنگام ساخت | رشتهٔ آمادهٔ «۳۰ دی ۱۴۰۴» |
| نمایهٔ جست‌وجو | هنگام ساخت | یک JSON که با نخستین کلید واکشی می‌شود |
| تمِ روز/شب | هنگام اجرا | چند متغیر CSS |
| مسیریابی | هنگام اجرا | حدود ۵۰ خط `pushState` |

![نمودار مراحل ساخت، از پروندهٔ متنی تا HTML ایستا](/media/architecture.svg "از پروندهٔ متنی تا HTML ایستا: هر کاری که می‌شود پیش از انتشار انجام داد، پیش از انتشار انجام می‌شود.")

ستون سوم همان چیزی است که کاربر دانلود می‌کند. نکتهٔ ظریف این است که ستون
دوم هرچه پرتر شود، ستون سوم لاغرتر می‌شود ــ و این وارونهٔ چیزی است که
معمولاً در پروژه‌ها اتفاق می‌افتد.

## برجسته‌سازی، بی‌برجسته‌ساز

مشکل روشن است: Shiki رنگ‌ها را به‌صورت `style="color:#..."` درونِ HTML
می‌نشاند، و آن رنگ ثابت است. اما این وب‌سایت سه تم دارد.

راه‌حل این است که به‌جای یک تم، سه تم بدهیم و از Shiki بخواهیم هیچ‌کدام را
پیش‌فرض نکند:

```javascript
hl.codeToHtml(code, {
  lang,
  themes: { day: 'neveshtar-day', sepia: 'neveshtar-sepia', night: 'neveshtar-night' },
  defaultColor: false,       // هیچ رنگی را مستقیم ننشان
  cssVariablePrefix: '--s-',
});
```

خروجی، به‌جای یک رنگ، سه متغیر می‌گیرد:

```html
<span style="--s-day:#14213D;--s-sepia:#2B2F4A;--s-night:#A9BDE0">theorem</span>
```

و انتخاب میانشان کارِ CSS می‌شود ــ که یعنی کارِ هیچ‌کس:

```css
.code-block span { color: var(--s-day); }
:root[data-theme="sepia"] .code-block span { color: var(--s-sepia); }
:root[data-theme="night"] .code-block span { color: var(--s-night); }
```

تعویض تم، هزینه‌اش صفر جاوااسکریپت است. مرورگر خودش متغیر تازه را حل می‌کند.

## ریاضیات، بی‌قلم

KaTeX معمولاً HTML تولید می‌کند و به `katex.min.css` و حدود بیست پروندهٔ
قلم نیاز دارد ــ چیزی حدود ۳۰۰ کیلوبایت برای نمایش یک $E = mc^2$.

اما KaTeX یک حالت دیگر هم دارد:

```javascript
katex.renderToString(tex, { output: 'mathml', throwOnError: false });
```

خروجی، MathML خالص است: نشانه‌گذاریِ استانداردی که مرورگر خودش می‌چیندش.
صفر بایت CSS، صفر بایت قلم، صفر بایت جاوااسکریپت.

یک نکتهٔ ظریفِ راست‌به‌چپ هم هست: فرمول جزیره‌ای لاتین در متنی فارسی است و
بدون جداسازیِ صریح، ترتیبش به‌هم می‌ریزد.

```css
.math { direction: ltr; unicode-bidi: isolate; }
```

## آنچه از دست می‌رود

انصاف حکم می‌کند که هزینه را هم بنویسم.

- **محتوا دیگر بی‌ساخت منتشر نمی‌شود.** وب‌سایتِ پیشین وعده می‌داد که پس از
  نخستین انتشار هرگز لازم نیست دوباره بسازی. با پیش‌رندر، این وعده از دست
  می‌رود: عنوان و کارت اجتماعیِ هر نوشته باید *پیش از* آن‌که خزنده بپرسد،
  در پرونده‌ای روی دیسک باشد.
- **بازسازیِ کامل، در برابر انتشار افزایشی.** با صد نوشته این چند ثانیه
  است؛ با هزار نوشته باید به فکر بود.
- **MathML برای فرمول‌های بلند به‌خوبیِ KaTeX نیست.** کسرهای تودرتو و
  ماتریس‌های بزرگ در مرورگر کمی بدتر می‌نشینند. راه فرار باز گذاشته شده:
  یک متغیر محیطی، و همه‌چیز به حالت HTML برمی‌گردد.

هیچ‌کدام از این‌ها فاجعه نیست. اما هیچ‌کدام هم صفر نیست ــ و نوشتنشان بخشی
از همان صداقتی است که قاعدهٔ اول ایجابش می‌کند.

## نتیجه

بستهٔ جاوااسکریپتی که به مرورگر می‌رسد چیزی حدود ۴۵ کیلوبایت فشرده است، و
بیشترش React است. اگر روزی React هم برود، عدد به چند کیلوبایت می‌رسد.

سؤال درست این نیست که «چه کتابخانه‌ای برای این کار هست؟» ــ سؤال درست این
است که «این کار را می‌شود هنگام ساخت انجام داد؟» و پاسخ، بیشتر از آنچه
انتظار داری، بله است.
